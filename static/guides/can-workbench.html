How it fits

The workbench is a viewer for decisions already made elsewhere. It does not search for signals, fit formulas, or promote a field into the bus map or telemetry. Field selections are local to one investigation; docs/bus-map.md stays the canonical decode list.

Generate a report

Try the synthetic example

Run from the repository root. The fixture is software test data, not vehicle evidence.

cd ~/dev/obd-things
python3 tools/can_workbench_report.py \
  tests/fixtures/can_workbench/investigation.json \
  --out tmp/can_workbench/demo
open tmp/can_workbench/demo/index.html

Keep bundle.json beside the HTML; the report's download link points to it. --out must be a directory that does not exist yet.

Run your own investigation

  1. Make a folder for the investigation (under tmp/, which is gitignored) and write investigation.json there. Relative paths resolve beside the manifest.
  2. Point each capture's path at a finalized candump file. Files that are still being written will fail the before/after hash check.
  3. Add each field with geometry taken from the bus map or a reviewed analysis, and record where it came from in provenance.
  4. Generate, then narrow with --capture, --field and --window if you need full detail for a short span.
python3 tools/can_workbench_report.py tmp/my-question/investigation.json \
  --field battery_voltage --window 30 90 --gap-seconds 0.5

Without --out, each run lands in a fresh tmp/can_workbench/report-<UTC timestamp>/. Earlier reports are never overwritten. The exact command, Python version, tool hashes and input hashes are stored in the bundle.

CLI options

--field NAMEallSelect a field by manifest name. Repeatable.
--window START ENDwhole captureInclusive elapsed seconds from each capture's first valid frame. Statistics then cover only this window.
--gap-seconds S1A larger spacing between observations counts as a gap and breaks the plotted line. Set it to the signal's normal cadence.
--max-points N2,000Plotted points per series (4–20,000). Counts, minima, maxima and gaps always use every observation.

Write a manifest

Required top-level keys are schema_version (1), title, summary, captures and fields. Optional: questions, next_checks, references, analyses. Unknown keys are rejected, so typos fail loudly.

{
  "schema_version": 1,
  "title": "Charging voltage at idle",
  "summary": "Does the candidate track the meter reading?",
  "questions": ["Does it lag the meter during load changes?"],
  "next_checks": ["Repeat with headlights on."],
  "captures": [
    {"name": "idle", "path": "idle.log",
     "channels": {"can0": "B-CAN"},
     "conditions": "Engine idling, no accessories"}
  ],
  "fields": [
    {"name": "battery_voltage", "bus": "B-CAN", "channel": "can0",
     "can_id": "46C", "id_bits": 11, "dlc": 8,
     "field": {"dbc_start_bit": 36, "length_bits": 13,
               "byte_order": "big", "signed": false},
     "scale": 0.0025, "offset": 0, "unit": "V",
     "evidence_tier": "verified_decode",
     "provenance": "docs/bus-map.md 0x46C system voltage, low 13 bits"}
  ],
  "references": ["meter.json"],
  "analyses": []
}

The field matches the bus map's verified 0x46C voltage decode (bytes 4–5 big-endian, mask 0x1FFF, ÷ 400). The capture and reference names are examples. Check the bus map for the current definition before reusing it.

Captures

KeyMeaning
nameUnique label used by --capture and the report.
pathcandump text log, optionally .zst. Read-only.
channelsEvery recorded interface mapped to a bus name, e.g. {"can0": "B-CAN"}. Required for every channel in the file; routing is never guessed from CAN IDs.
conditionsWhat the vehicle was doing. Use unknown when you don't know; a filename alone isn't evidence.

Each capture keeps its own clock. When comparing stream inventories, the first selected capture is the baseline, and only interfaces mapped to the same bus in both captures are compared.

Fields

KeyMeaning
bus, channelMust match a capture mapping exactly. A field is not looked for on other buses.
can_idHex string without 0x. 11-bit 123 and 29-bit 00000123 are different streams.
id_bits, dlc11 or 29; exact payload length. Frames with another DLC are excluded.
fielddbc_start_bit, length_bits, byte_order (little or Motorola big), signed. Same extractor as the rest of the repo.
scale, offset, unitPlotted value is raw × scale + offset. Use unit raw when unknown.
evidence_tierOne of the three tiers below.
provenanceRequired. Where the definition came from.
supporting_evidence, contradicting_evidenceOptional lists of notes shown with the field.

Evidence tiers

exploratory_candidateA guess worth plotting, such as a correlator hit.
operational_proxyGood enough to use, not proven to be the physical quantity.
verified_decodeConfirmed against an independent measurement.

The tier is a label you supply. The tool displays it and checks nothing about it.

References and analyses

Reference readings

A reference file holds independent observations (meter, scan tool, phone log) for one capture and field. They are drawn in orange on the same plot.

{
  "schema_version": 1,
  "capture": "idle",
  "field": "battery_voltage",
  "name": "Multimeter at battery",
  "unit": "V",
  "provenance": "Hand-logged; clock aligned to capture start by ...",
  "timestamp_basis": "capture_clock",
  "observations": [
    {"timestamp": "1696000012.500", "value": 14.21}
  ]
}
  • Timestamps are strings on the capture's own clock. Numeric timestamps are rejected. Align clocks yourself first and say how in provenance.
  • The unit must match the field's unit. There is no interpolation or resampling.
  • An empty observations list means “no reference”, and is shown that way. A missing file is an error.

Correlator reports

analyses takes existing schema-1 JSON output of can_timeseries_correlate. The report shows its ranked candidates, rejections and settings, marked exploratory. Imported candidates are not attached to your fields automatically, and no analysis tool runs when the report is generated or opened.

Read the report

SectionWhat it shows
Recordings & conditionsEach capture's channel→bus mapping, frame count, exact first/last timestamp, malformed or unterminated line counts, and the inventory comparison between captures.
Inspect a fieldPick recording and field. Metrics, then a plot of the field (teal) and references (orange). The start/end boxes filter plotted points only.
Candidate evidenceImported correlator reports, open questions and next checks from the manifest.
Reproduce & exportExact command, environment, tool and input hashes, the original manifest, and the bundle.json download.

Series status

varyingTwo or more observations with different values.
constantEvery observation is the same value. Can't show a relationship to anything.
insufficientExactly one observation.
missingNo matching frames for that channel, ID, ID width and DLC in the selected range.

If the field's bus and channel are not mapped in the chosen recording, the plot says so. The field is not looked for on another bus.

The plot is decimated with a fixed stride. A short spike or a brief segment can be missing from the line even though it is in the min/max and counts. For full detail, regenerate with a narrower --window.

Troubleshooting

Message or symptomFix
output already exists; choose a new directoryPass a new --out, or omit it to get a timestamped directory.
unknown or empty field selectionThe --field or --capture name doesn't match the manifest's name.
window must be ordered, nonnegative elapsed secondsUse --window START END with 0 ≤ START ≤ END.
FILE:LINE: timestamps decreaseThe capture isn't in time order. Split it at the jump or sort it upstream, and note that in conditions.
input changed during generation: PATHA capture was still being written. Use a finalized copy.
.zst fails or is truncatedInstall zstd (brew install zstd) and check the archive with zstd -t FILE.
Field shows missingCheck channel, can_id, id_bits and dlc against the capture's summary in the Recordings section; all four must match.

Limits and rules

  • Up to 16 captures, 64 fields, 32 reference files and 32 analysis files per report; 16 MiB per JSON input; 64 KiB per capture line; 4,096 streams per capture inventory.
  • Captures are streamed, so large and compressed logs are fine. A 250,000-frame synthetic capture took about 2.5 s.
  • Different captures are never time-aligned to each other. Elapsed seconds count from each capture's own first frame.
  • Generated reports contain file paths and raw statistics. Treat them as private evidence and review before sharing.
  • Output stays under the gitignored tmp/. To keep a report, promote it deliberately into projects/<project>/findings/ next to the analysis that cites it.
