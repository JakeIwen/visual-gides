mwan3-adaptive

Use
Automatically adjust how new connections share available WAN links.
Requires
A working classic mwan3 installation with an existing balanced policy.
Service costs
No additional relay, VPS or subscription. Existing internet service and data charges still apply.
Version
0.2.0-r1 · local candidate Live router testing remains.

How the pieces fit

  1. 1. CheckStopped service; validate compatible chains.
  2. 2. ObserveLearn and recommend; apply no new weights.
  3. 3. ActiveAdjust shares for new connections.
  4. 4. StopRestore current configured mwan3 weights.

Configure and start

Keep your working mwan3 configuration. This package learns from uplink traffic and congestion, then adjusts the distribution of new connections within existing policies.

Project status: mwan3-adaptive is an independent companion, not part of mwan3 or OpenWrt and not endorsed or supported by either project. Version 0.2.0-r1 is a local candidate awaiting review and validation; no release archive or package repository has been published. Its stock mwan3 package dependency is standard, but the internal policy-chain layout it modifies is not a stable public API. Recheck compatibility after upgrades.

Before enabling: use classic mwan3, including its iptables-nft compatibility backend. A policy needs two enabled, available members at the same metric to use both concurrently. Native nftables forks with different chains are unsupported. Unknown chain layouts are left untouched.

1. Check prerequisites and install

Start with working classic mwan3 and two available uplinks. This package does not create WAN interfaces, routing policies or matching traffic rules. A higher metric is a backup tier: two interfaces must use the same metric to balance concurrently.

Router SSH shell · inspect
ubus call system board
mwan3 status
mwan3 policies
uci show mwan3

These are illustrative native mwan3 member/policy sections, not a replacement configuration. Here both links are in metric 1, and the initial static weights are equal. wan and wanb must already exist, be enabled and online; a native mwan3 rule must target balanced. Configured literal track_ip addresses supply the latency signal; without them the adapter can still learn from traffic counters.

/etc/config/mwan3 · example excerpt
config member 'wan_m1'
    option interface 'wan'
    option metric '1'
    option weight '1'

config member 'wanb_m1'
    option interface 'wanb'
    option metric '1'
    option weight '1'

config policy 'balanced'
    list use_member 'wan_m1'
    list use_member 'wanb_m1'

Build from the reviewed candidate source in a configured OpenWrt tree or SDK matching your firmware release. The package is Lua/shell; its dependencies still need to match the firmware. There is no public package feed for this candidate.

Configured OpenWrt build tree · build host, not router
./scripts/feeds update packages &&
./scripts/feeds install mwan3 iputils-ping &&
make menuconfig &&
make package/network/config/mwan3-adaptive/compile V=s

Select Network → Routing and Redirection → mwan3-adaptive. If mwan3 is hidden, enable rpcd. In an SDK, copy the package directory to package/mwan3-adaptive and use make package/mwan3-adaptive/compile V=s. See the candidate README for the source layout.

Copy the matching built artifact to the router’s /tmp. Replace the example source path and ROUTER; use the actual .ipk or .apk format produced for that release.

Installation leaves adaptation disabled and sets observation as its default mode. Check the installed version with mwan3-adaptive --version before proceeding.

2

Choose the policy to observe

Find existing names with mwan3 policies or uci show mwan3. Native mwan3 rules must already send the desired traffic to that policy. The name below is an example, not a detected policy.

The commands replace the adaptive package’s previous policy selection. They do not edit mwan3 policies. Keep metered links out of the selected policies if they should not carry extra traffic.

Router SSH shell · observation
uci set mwan3-adaptive.main.enabled='1' &&
uci set mwan3-adaptive.main.mode='observe' &&
(uci -q delete mwan3-adaptive.main.policy || true) &&
uci add_list mwan3-adaptive.main.policy='balanced' &&
uci commit mwan3-adaptive &&
/etc/init.d/mwan3-adaptive stop &&
/usr/sbin/mwan3-adaptive check &&
/etc/init.d/mwan3-adaptive enable &&
/etc/init.d/mwan3-adaptive start

Download buttons save shell scripts; they never run them. Review the file, transfer it to the router, then run it there. For the observation script, replace ROUTER below with your router’s SSH address.

Mac Terminal · transfer the downloaded script
scp ~/Downloads/mwan3-observe.sh root@ROUTER:/tmp/
Router SSH shell · run the reviewed script
sh /tmp/mwan3-observe.sh

3. Generate ordinary traffic and inspect the result

The generated sequence stops the service, runs mwan3-adaptive check, then starts observation. The check validates configuration and recognized active chains using a RAM-only snapshot. It requires the daemon to be stopped and performs no network probes or firewall writes.

Use several independent downloads or normal activity across your devices. Observation measures traffic and sends bounded probes, but does not apply new weights. The stop/start sequence restores previously applied weights before observation begins; a failed stop prevents the check and start.

Router SSH shell
mwan3-adaptive status

Sampling pauses 10 seconds between completed cycles by default. Allow several cycles under traffic; an idle link’s unused capacity cannot be measured from traffic counters.

4. Enable automatic adjustments

When the recommendations look sensible, switch to active mode. Existing connections keep their uplink; the updated distribution affects new connections.

Router SSH shell · changes allocation
uci set mwan3-adaptive.main.mode='active' &&
uci commit mwan3-adaptive &&
/etc/init.d/mwan3-adaptive stop &&
/etc/init.d/mwan3-adaptive start

mwan3 decides eligibility

It owns routing, tracking, failover tiers, sticky rules and connection marks. Higher-metric links remain backups.

Adaptive learns the distribution

Traffic rates, latency growth and loss influence new connections. A small exploration share keeps eligible links in use so improvements can be noticed.

Daily commands

Return to observation

The successful stop matters: it restores the current configured mwan3 weights before observation starts. Changing only the mode can leave previously applied weights in place.

Router SSH shell
uci set mwan3-adaptive.main.mode='observe' &&
uci commit mwan3-adaptive &&
/etc/init.d/mwan3-adaptive stop &&
/etc/init.d/mwan3-adaptive start

Stop adaptation and keep it stopped after reboot

Router SSH shell · restore configured weights
/etc/init.d/mwan3-adaptive stop &&
/etc/init.d/mwan3-adaptive disable

Stop restores owned or safely adopted pending policies using current active members and current configured mwan3 weights. It does not replay a saved firewall snapshot. Successful restoration clears both ownership ledgers. The second command runs only if stop succeeds. Stop successfully before uninstalling.

If restoration fails

Read the error, confirm the daemon has stopped, then retry restoration:

Router SSH shell
mwan3-adaptive restore

Native mwan3 continues to own failover. A native policy rebuild also replaces adaptive allocations with its configured weights.

Take a single sample with the daemon stopped
Router SSH shell · no routing changes
mwan3-adaptive sample

This probes and writes RAM status, but has no throughput history. It is not a speed test and cannot run alongside the daemon.

Validate configuration and chain compatibility
Router SSH shell · daemon stopped
mwan3-adaptive check

This validates the effective configuration and recognized active classic mwan3 chain layout. It uses a RAM-only snapshot and performs no probes or firewall writes.

Reading the status

Example output from observation mode:

Example · not live telemetry
current_uptime=12345.00
sample_uptime=12343.00 interval=10 enabled=1 mode=observe result=observed
ipv4:balanced wan  sampled=1 recommended=800 rx
ipv4:balanced wanb sampled=1 recommended=200 rx
link=wan  rx_kbit=24000.0 tx_kbit=900.0 quality=0.950
link=wanb rx_kbit=6000.0  tx_kbit=200.0 quality=0.700
FieldMeaning
sampledThe policy weights at the start of the cycle. Here, 1 and 1 mean equal shares.
recommendedProportional weights within this policy and address family. Here, 800 + 200 = 1,000: about 80% and 20% of new connections.
rx / txThe traffic direction used for that recommendation: download or upload.
qualityA smoothed internal preference from latency growth and probe loss. It is not an uptime percentage or speed measurement.
Uptime fieldsSeconds since router boot. Subtract sample uptime from current uptime to judge freshness. A status file can remain after the service stops.

Result values

observedA meaningful recommendation was prepared without applying it.
appliedThe changed policies now use the recommended allocation.
unchangedNo policy was ready for a meaningful update. The difference may be small, the cooldown may still apply, or measurements may be incomplete.
restoredCurrent configured static weights were reapplied to the owned (or safely adopted pending) policy chains.
errorThe cycle failed. A later-family failure triggers compensation of earlier writes when possible, but a crash or failed rollback can require journal recovery.

Tuning

Start with the defaults. Settings live in /etc/config/mwan3-adaptive, in section main. After editing, commit the configuration, then stop the service successfully before starting it again.

OptionDefaultEffect
interval10 secondsDelay after a completed sampling cycle. Allowed: 5–300, whole seconds.
update_interval30 secondsMinimum spacing between updates to a policy. Allowed: 5–3,600; at least interval.
hysteresis0.10Minimum total redistribution of share before applying a change. Allowed: 0.01–0.50.
exploration0.05Total allocation reserved across eligible links for learning. Allowed: 0.01–0.50.
congestion_ms30 msLatency growth that halves the instantaneous latency preference. Allowed: 5–1,000.

Apply a tuning change

This example slows updates to once per minute while preserving your current mode and policy selection. Start with the defaults; change one option at a time.

Router SSH shell · example tuning
uci set mwan3-adaptive.main.update_interval='60' &&
uci commit mwan3-adaptive &&
/etc/init.d/mwan3-adaptive stop &&
/usr/sbin/mwan3-adaptive check &&
/etc/init.d/mwan3-adaptive start

Learning resets on restart. Learned allocations and observations stay in private RAM files under /var/run/mwan3-adaptive.

Troubleshooting

Stop, restart or uninstall reports a restoration failure

Leave the controller stopped. Inspect logread -e mwan3-adaptive and native mwan3 status, then retry mwan3-adaptive restore. Do not delete its pending journal to force a restart. A successful restoration uses current native membership and configured weights; it does not replay an old firewall snapshot. Stop successfully before removing the package with opkg remove mwan3-adaptive or apk del mwan3-adaptive.

A selected policy says “shared interface counters”

Its active logical interfaces map to the same L3 device, so independent capacity cannot be learned from those counters. That policy is skipped. Inspect the underlying interfaces; do not treat duplicate counters as two independent uplinks.

No samples recorded, or the timestamp stopped advancing

Check that the package is enabled in UCI and the daemon is running. A successful start alone proves little when main.enabled is 0. Look at service logs:

Router SSH shell
logread -e mwan3-adaptive
One link gets no new connections

Check native mwan3 status and policy membership first. Both members must be enabled, online and eligible at the same metric. Sticky rules can also pin new connections. This package does not promote a backup tier or override sticky behavior.

Router SSH shell
mwan3 status
Recommendations barely move

Generate more independent connections and allow several cycles. A single existing transfer cannot be split or moved. Small differences are deliberately suppressed by hysteresis; changes also wait for the update interval.

Check interface counters and configured literal track_ip targets. No tracking target means no latency signal. Shared devices, offloading and shared upstream bottlenecks can obscure capacity.

“Classic mwan3 iptables hook unavailable” or a skipped layout

Confirm that classic mwan3 is running and has created its normal chains. Native nftables forks use a different contract and need another adapter. Unknown layouts are left untouched.

“Firewall changed, stopped, stale, or transaction failed”

The controller could not safely apply that snapshot. Native hotplug changes, a stop request, an old sample or a firewall error can cause this. It retries from fresh state. Persistent failures need log inspection; do not clear conntrack or manually overwrite policy chains to work around them.

Scope and verification

  • Connection balancing, not single-flow bonding. No external relay or subscription. One connection uses one uplink; summed speed is not guaranteed.
  • Failover does not migrate existing sessions. A failed uplink can break sessions using its public IP.
  • Data caps are not tracked. Restrict metered uplinks through the native policy selection.
  • Capacity estimates are heuristic. They depend on traffic and are not speed-test measurements. This does not replace SQM.
  • Cross-family writes are not atomic. Both families are preflighted before writes and a later failure triggers compensation, but a crash or rollback failure can leave a partial change. The retained pending journal is reconciled on recovery.

The source includes algorithm, controller/lifecycle, package-content and isolated Linux network-namespace checks. Their presence does not mean every revision passed every check. Consult validation records for the exact source revision and environment; an IPv6 packet check may be skipped on kernels without IPv6 support. No universal router, radio or workload compatibility is claimed.
